# zclaw 信頼性設計書（Discord + LLM連携）

このドキュメントは、最近実装した「空応答」「Discord送信失敗」「TLS/通信競合」対策を、初学者向けに整理した設計書です。

## 1. 何が問題だったか

実運用ログで次の症状が出ていました。

- LLM APIは `200 OK` なのに、`content=""`（空文字）で返る
- `finish_reason=length` が出る
- Discord送信が `status=400` で失敗することがある
- Discord polling と LLM request が同時に走り、接続エラーが散発する

## 2. 根本原因（今回の整理）

主な原因は1つではなく、複合でした。

1. モデル出力側の問題
- GPT-5系で、内部推論や長い文脈の影響により、可視テキストが空のまま `length` で打ち切られるケースがある

2. 文字列処理側の問題
- 固定長バッファへの切り詰めでUTF-8境界を壊すと、Discord側でJSON/文字列として不正扱いされ `400` になる可能性がある

3. ネットワーク利用側の問題
- 1台のESP32上でDiscordとLLMが同時にTLS/HTTPを張ると、タイミング次第で失敗しやすい

## 3. 目標

- 「失敗しにくい」ことを最優先にする
- 失敗しても自動回復する
- 回復しない場合は文脈を切って次の成功率を上げる

## 4. 実装方針（全体像）

### 4-1. 通信の排他制御

- 共有HTTPロックを導入し、DiscordとLLMの同時接続を避ける
- 競合時は「短時間で諦めて次回に回す」方針

対象ファイル:
- `main/net_http_guard.c`
- `main/llm.c`
- `main/discord.c`

### 4-2. UTF-8安全な文字列処理

- 新規ユーティリティで「UTF-8文字の途中切断」を防止
- 履歴保存、応答連結、Discord送信分割のすべてで同じルールを使う

対象ファイル:
- `main/utf8_utils.c`
- `main/utf8_utils.h`
- `main/agent.c`
- `main/json_util.c`
- `main/discord.c`

### 4-3. 空応答への段階的リカバリ

- 1回目で空なら、同一ターン内で1回だけ再試行
- 再試行時は「短い回答」「ツール禁止」「文脈を最小化」
- それでも空なら、その会話履歴を全クリアして次ターンをクリーンにする

対象ファイル:
- `main/agent.c`

### 4-4. 出力長の制約

- 通常応答: 200〜300文字、2〜4文をデフォルト
- 空応答再試行: 120文字以内、2文以内

対象ファイル:
- `main/agent.c`（システムプロンプト拡張 + リトライヒント）

## 5. 処理フロー（現在）

### 5-1. 通常ターン

1. ユーザー入力を履歴に追加  
2. リクエストJSONを構築  
3. LLM API呼び出し（リトライあり）  
4. 応答をパース  
5. テキストなら送信、ツール呼び出しなら実行して次ラウンドへ

### 5-2. 空応答時

1. `text_out == ""` かつ `tool_callsなし` を検出  
2. 1回だけ再試行  
   - 最新ユーザー入力だけで再リクエスト
   - ツールは無効
   - 短文制約を強化  
3. それでも空なら履歴全クリア  
4. ユーザーへ「リセットしたので再入力して」と返す

## 6. 「12回分の会話」について

設定値:
- `MAX_HISTORY_TURNS = 12`

意味:
- 基本は「ユーザー/assistantペアの上限」を12として設計

注意:
- ツール利用時は `tool_use` / `tool_result` も履歴に入るため、体感上の会話ターンは12未満になることがあります

## 7. Discord 400対策の要点

今回の対策は2層です。

1. 送信前分割  
- 2000文字上限を超える文を複数メッセージに分割

2. UTF-8境界保証  
- 分割点とバッファ終端をUTF-8安全に扱う

加えて:
- 4xx時にレスポンス本文をログ出力し、原因追跡できるようにした

## 8. モデル空応答（`finish_reason=length`）対策の要点

- OpenAI GPT-5系では `max_completion_tokens` を利用
- `reasoning_effort=minimal` を付与して「見える本文」を優先
- 空応答時は再試行プロンプトを短文化し、文脈を圧縮
- 最終手段として履歴クリア

## 9. 失敗時の観測ポイント（ログ）

見るべきログ:

- `json: OpenAI response had no text/tool_calls ...`
- `finish_reason=length`
- `discord: Discord HTTP send failed: status=400`
- `discord: Discord error response: body=...`
- `agent: Model returned empty response without tool_calls; retrying once`
- `agent: Clearing full conversation history ...`

## 10. 初学者向け: 変更するときの順番

1. まず `agent.c` でフローを読む  
2. 次に `json_util.c` でリクエスト/レスポンスの形を確認  
3. `discord.c` で送受信制限（2000文字）を確認  
4. 最後に `utf8_utils.c` で切り詰めルールを理解する

## 11. 今後の改善候補

- 履歴を「固定件数」ではなく「トークン見積もり」で管理
- Discord送信を「段落単位優先」で分割（読みやすさ改善）
- 空応答が連続したらモデル/設定を自動フォールバック
- 重要エラーをメトリクス化して可視化

## 12. まとめ

今回の設計は「一発で完璧」ではなく、次の順で堅牢化しています。

1. 競合を減らす（HTTP排他）  
2. 壊れにくくする（UTF-8安全処理）  
3. 壊れても回復する（再試行 + 文脈縮小）  
4. 回復しなければ切り離す（履歴クリア）

この4段構えで、実運用の失敗率を下げる方針です。
